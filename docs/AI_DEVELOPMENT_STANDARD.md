# Стандарт архитектурных решений для AI-разработки

Этот документ задаёт политику выбора решений для AI-ассистентов, Codex и других автоматизированных исполнителей проекта.

## Главный принцип

Не выбирай решение только потому, что оно требует минимального количества строк или быстрее всего закрывает локальный симптом.

Выбирай минимальный рабочий срез той архитектуры, которая:

1. естественно расширяет существующие системы;
2. соответствует утверждённым игровым правилам;
3. не создаёт параллельную реализацию;
4. сохраняет совместимость данных и сохранений;
5. подходит для будущих механик того же класса;
6. остаётся производительной на Android;
7. допускает автоматическую проверку;
8. не создаёт преждевременно крупную систему без реального сценария использования.

## Иерархия выбора

При нескольких вариантах оценивай их в следующем порядке:

1. обязательные ограничения проекта и версия Godot;
2. корректность игровых правил и тайминга;
3. совместимость с существующей архитектурой;
4. пригодность для ближайших утверждённых механик;
5. совместимость сохранений и стабильность идентификаторов;
6. производительность и управление на Android;
7. тестируемость и диагностируемость;
8. стоимость реализации и размер изменения.

Размер diff не является главным критерием. Он используется только после более важных критериев.

## Обязательный анализ перед изменением

Перед написанием кода:

- проверь README и закреплённую версию Godot;
- проверь текущую ветку и связанные pull request;
- найди существующую точку расширения;
- определи владельца правила: данные, доменная система, runtime или UI;
- проверь, какие ближайшие механики должны использовать тот же контракт;
- оцени влияние на сохранения, Android и тесты.

Если существуют два реалистичных варианта, кратко сравни их. Выбирай вариант с лучшим архитектурным соответствием, а не просто самый короткий.

## Правило минимальной правильной архитектуры

Не нужно заранее строить всю финальную систему. Нужно реализовать минимальный работающий вертикальный срез правильной архитектуры.

Пример:

- неправильно: добавить отдельное окно и отдельный обработчик для каждой новой реакции;
- также неправильно: заранее строить универсальный движок событий для всех возможных механик игры;
- правильно: выделить общий координатор реакций после того, как появились несколько реально работающих типов реакций, подключить к нему один полноценный боевой сценарий и покрыть контракт тестами.

## Разделение ответственности

- JSON/ресурсы содержат определения игровых данных.
- Доменные системы проверяют доступность и рассчитывают эффект.
- Runtime связывает доменные результаты со сценами, HP, ресурсами, анимациями и ходами.
- UI отображает варианты и не содержит правил конкретного класса или персонажа.
- Сохранения хранят стабильные ID и состояние, а не ссылки на UI-узлы.

## Запреты

Не допускается:

- дублировать систему ради быстрого локального исправления;
- помещать игровые правила внутрь кнопок или конкретной сцены;
- привязывать общий UI к одному классу или персонажу;
- вводить магические строки вместо стабильных ID;
- переписывать рабочий слой целиком без доказанной необходимости;
- называть инфраструктуру завершённой, если она не подключена хотя бы к одному реальному сценарию;
- добавлять абстракцию, для которой нет текущего или ближайшего подтверждённого использования.

## Формат решения в отчёте

Для нетривиальной задачи укажи:

- какой локальный вариант был самым простым;
- почему он не выбран, если ухудшал будущее расширение;
- какая существующая точка расширения использована;
- какие ближайшие механики смогут использовать новый контракт;
- какие файлы изменены;
- что проверено;
- какие ограничения ещё остаются.

## Definition of Done

Архитектурное изменение завершено, когда:

- есть реальный подключённый сценарий;
- новые доменные правила покрыты unit-тестами;
- интеграция покрыта smoke-тестом или существующей регрессией;
- импорт Godot проходит без parser errors;
- мобильные проверки не ухудшены;
- старые сохранения имеют fallback, если менялись данные;
- создан отдельный PR;
- PR не объединён без прямого подтверждения пользователя.
