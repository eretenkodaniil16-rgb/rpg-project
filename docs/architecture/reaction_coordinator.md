# Координатор реакций

## Назначение

`ReactionCoordinator` является единой точкой сбора, сортировки и разрешения реакций нескольких участников боя. Он не заменяет конкретные правила заклинаний и классовых особенностей. Системы `ReactionOpportunitySystem`, `SpellReactionSystem`, `DefensiveReactionSystem` и `DamageFallReactionSystem` продолжают отвечать за доступность и эффект конкретной реакции.

Координатор решает другую задачу: кто может реагировать на одно событие, какие варианты должны появиться в одном окне, в каком порядке обрабатываются контроллеры и когда дальнейшая цепочка должна остановиться.

## Основные объекты

### ReactionEvent

Хранит:

- стабильный `event_id`;
- `trigger_id`;
- источник и цель;
- общий контекст события;
- статус жизненного цикла;
- историю выбора и разрешения;
- уже обработанных участников;
- признак остановки дальнейшей цепочки.

Статусы:

1. `OPEN` — варианты ещё можно предлагать;
2. `RESOLVING` — выбранная реакция разрешается;
3. `RESOLVED` — событие завершено;
4. `CANCELLED` — событие отменено вызывающей системой;
5. `INVALIDATED` — исходное событие больше не существует или цель стала недопустимой.

### ReactionCandidate

Отделяет боевой узел от игровых данных персонажа. Это позволяет использовать один координатор для:

- игрока;
- управляемых игроком союзников;
- дружественных NPC;
- противников;
- временных призванных существ;
- будущих существ без полного `PlayerCharacter`, если реакция не требует данных заклинателя.

Кандидат содержит `reactor_id`, `actor`, `character`, команду, контроллер, инициативу, доступность реакции и локальные переопределения контекста.

### ReactionCoordinator

Координатор:

- собирает варианты через существующий `ReactionOpportunitySystem`;
- создаёт уникальные ID, если несколько существ предлагают одинаковую реакцию;
- сохраняет старый ID при единственном реагирующем существе;
- объединяет всех существ одного контроллера в одно окно выбора;
- сортирует варианты по приоритету реакции, затем по инициативе;
- предоставляет детерминированный выбор для AI;
- записывает историю;
- останавливает цепочку, если исходное событие предотвращено или инвалидировано.

## Контракт узла-участника

Будущий союзник или противник может войти в систему без прямой зависимости координатора от его класса. Узел должен реализовать:

```gdscript
func get_reaction_candidate_descriptor(
    trigger_id: String,
    event_context: Dictionary,
    source: Node,
    target: Node
) -> Dictionary:
```

Пустой словарь означает, что узел не участвует в этом событии.

Поддерживаемые поля результата:

- `reactor_id: String`;
- `character: PlayerCharacter`;
- `display_name: String`;
- `team_id: String`;
- `controller_id: String`;
- `initiative: int`;
- `reaction_available: bool`;
- `can_react: bool`;
- `context_overrides: Dictionary`;
- `metadata: Dictionary`.

Узлы вне текущей инициативы могут быть добавлены в группу `reaction_reactors`.

## Порядок разрешения

1. Игровая система создаёт `ReactionEvent` до необратимого изменения, если реакция предотвращает событие, либо после изменения, если этого требует правило.
2. Координатор собирает кандидатов.
3. Для каждого кандидата вычисляются конкретные доступные варианты.
4. Одинаковые варианты разных существ получают составные selection ID.
5. Варианты группируются по `controller_id`.
6. Игрок видит одно окно для всех управляемых им существ.
7. AI выбирает вариант детерминированно по политике координатора.
8. Конкретная система правил разрешает выбранный эффект.
9. Боевой runtime расходует реакцию именно выбранного `reactor_actor`.
10. `ReactionEvent` решает, можно ли продолжать цепочку.

## Правила остановки цепочки

По умолчанию дальнейшие реакции прекращаются, если результат содержит один из признаков:

- `stop_reaction_chain`;
- `event_invalidated`;
- `countered`;
- `blocks_magic_missile`;
- `prevents_triggering_hit`.

Новые реакции не должны напрямую завершать координатор. Они возвращают семантический результат, а `ReactionEvent` принимает решение по общему контракту.

## Текущая интеграция

Вражеское сотворение заклинания уже проходит через координатор. Одиночный игрок сохраняет прежний ID `counterspell`, поэтому существующий UI и smoke-тесты остаются совместимыми. При добавлении второго доступного контрмага варианты автоматически становятся, например:

- `player:123::counterspell`;
- `companion:mage_01::counterspell`.

## Runtime-цикл одного события

Runtime не завершает `ReactionEvent` после первого выбранного варианта автоматически. После
каждого результата координатор повторно собирает доступные варианты того же события:

- использовавший или пропустивший реакцию участник исключается через
  `processed_reactor_ids`;
- если результат остановил исходное событие, очередь закрывается;
- если реакция не остановила событие, следующий допустимый участник получает свою
  возможность;
- исходное действие продолжается только после завершения всей очереди.

Это позволяет второму союзнику применить Контрзаклинание после неудачи первого, не создавая
новое событие и не теряя историю решений.

## Фильтр допустимых реакторов

Событие может ограничить получателей реакции данными:

- `eligible_reactor_ids` — стабильные ID реагирующих;
- `eligible_reactor_actor_ids` — instance ID боевых узлов текущего runtime.

Фильтр применяется в `ReactionEvent` до сбора конкретных вариантов. Поэтому Shield и Absorb
Elements предлагаются только существу, по которому попали или которое получает стихийный
урон, даже если рядом есть союзники с теми же подготовленными заклинаниями.

## Мигрированные runtime-пути

Через единый координатор проходят:

- Counterspell, включая последовательные попытки нескольких участников;
- Shield против попадания и Magic Missile;
- Absorb Elements до окончательного применения стихийного урона;
- подготовленная атака;
- атаки по возможности с повторной проверкой события после каждого реагирующего.

Правила, стоимость ресурсов и эффекты этих реакций остаются в профильных доменных системах.
Runtime отвечает только за сбор участников, показ решения, порядок и исполнение игрового
действия.

Следующие миграции должны переводить на этот же координатор:

1. защитные реакции на попадание и урон;
2. атаки по возможности нескольких существ;
3. подготовленные действия;
4. реакции союзников на чужие спасброски;
5. реакции врагов на действия игрока;
6. контрреакции и вложенные события.
